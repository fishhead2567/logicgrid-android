# logicgrid-android — roadmap

An Android app for the puzzles in
[logicgrid-puzzles](https://github.com/fishhead2567/logicgrid-puzzles),
generated by the [logicgrid](../logic_puzzles) Python package.

## Decisions already taken

| | |
|---|---|
| Composite grid | **first-class** — the primary solving surface, not a hint overlay |
| In-progress sync | **local only**. No account, no backend. |
| Default clue text | **narrative where one exists**, canonical otherwise |
| Missing narration | normal, not an error — 45 of 50 puzzles have none today |
| Licence | MIT, copyright `fishhead2567` |
| Progress key | **`pid`**, never the filename |

---

## 0. Will the composite grid fit? — measured, not guessed

The classic Penny Dell chart puts categories 2..N down the side and
1..N-1 across the top, using only the lower-left triangle. Across the current
50 puzzles:

| shape | puzzles | chart | usable cells |
|---|---|---|---|
| 3 × 4 | 7 | 8 × 8 | 48 |
| 3 × 5 | 3 | 10 × 10 | 75 |
| 4 × 4 | 6 | 12 × 12 | 96 |
| 4 × 5 | 18 | 15 × 15 | 150 |
| 5 × 5 | 9 | 20 × 20 | 250 |
| 5 × 6 | 7 | 24 × 24 | 360 |

Worst case is 24 columns. On a ~400dp phone:

| cell size | width | verdict |
|---|---|---|
| 44dp (Android min touch target) | 1056dp | 2.6× the screen |
| 32dp | 768dp | ~2× |
| 24dp | 576dp | 1.4× |
| 16dp | 384dp | fits, far too small to tap |

**Conclusion: it fits, but pan/zoom is mandatory rather than a nicety.** The
smallest 16 puzzles (3×4 through 4×4) fit at a comfortable 32–44dp with no
panning at all; the 5×6 ones never will. A paper puzzle is bigger than your
hand too, so this is the normal state of affairs, not a compromise.

The consequence that actually shapes the UI: **tap-to-cycle cannot be the only
input**, because below ~44dp you cannot reliably hit a cell. So:

- **tap selects** a cell. It highlights, and a status bar names it in full
  ("Marigold / third — unmarked"), exactly as the TUI's status line does.
- **O / X / clear buttons** act on the selection, and work at any zoom.
- **when cells are ≥44dp**, a second tap on the selected cell cycles it
  directly, so the fast path exists where it is safe.

That also solves label legibility: full names live in the status bar and the
sticky headers, so cells themselves need only hold a glyph.

## 1. Architecture

Three Gradle modules, chosen to put as much as possible under test **without a
device**:

```
:core   pure Kotlin/JVM. No Android dependencies at all.
        model, clue IR, the Board closure, (de)serialisation.
        -> plain JUnit tests, run in seconds, no emulator.

:data   Android library. Manifest sync, Room, repositories.
        -> JVM tests via MockWebServer + in-memory Room (Robolectric).

:app    Compose UI + ViewModels.
        -> ViewModels JVM-tested with fakes; Compose screenshot-tested on the
           JVM via Roborazzi; full UI tests on a device when one exists.
```

The split is not ceremony. The Python version put all the solving logic in a
UI-agnostic `board.py` with 29 tests, and that is exactly why the TUI was cheap
to write and cheap to change. `:core` is the same bet.

## 2. `:core` — the port

Ported from the Python, file by file:

| Python | Kotlin | notes |
|---|---|---|
| `model.py` | `Ref`, `Category`, `Schema`, `Solution` | value classes; `Ref` is a `data class` with a stable `compareTo` |
| `clues.py` | `sealed interface Atom` + 14 implementations | kotlinx-serialization, polymorphic on `"kind"` |
| `board.py` | `Board` | **the critical one** — the closure model |
| `csp.py` | `Grid`, propagation | only needed for *validate* and *hint*; not for play |

### The one thing that must be got right

`Board` stores **only the player's own marks** and recomputes everything they
force. Not storing derived marks is what makes editing sound: change your mind
about a cell and the consequences of the old answer vanish with it, rather than
lingering as X's nothing supports any more. It also makes undo a snapshot and
makes toggling assist a pure recompute.

Two levels of inference, as in the Python:

- **always on** — a circled cell rules out the rest of its row and column.
  That is the pencil-work the rules force, not a deduction.
- **assist, opt-in** — transitivity (A=B and B=C so A=C) and
  last-cell-standing. Those *are* deductions, so doing them unasked changes the
  puzzle.

### Conformance testing — the strongest guarantee available

Rather than only re-writing the 29 Python tests in Kotlin (which tests my
re-reading of them, not the port), generate **cross-implementation fixtures**:

1. A Python script walks each of the 50 puzzles, applies a deterministic
   pseudo-random sequence of marks, and after each one dumps
   `{marks, closure, answer, mistakes, solved}` to JSON.
2. A Kotlin test replays those fixtures through the Kotlin `Board` and asserts
   byte-identical closure at every step.

If the Kotlin diverges anywhere — in forced elimination, in assist, in conflict
detection — a fixture catches it, at the exact step it first differs. This is
cheap to build and far stronger than parallel hand-written tests.

Both `assist=false` and `assist=true` traces, since assist is the subtle half.

## 3. `:data` — content sync

Offline-first. The network is never on the critical path to playing.

1. The full 429 KiB content set is **bundled in `assets/`**, so a fresh install
   with no network has all 50 puzzles.
2. On startup, *in the background*, `GET manifest.json` from
   `raw.githubusercontent.com/fishhead2567/logicgrid-puzzles/main/`.
3. Compare each entry's `sha256` against the cache.
4. Download only what changed. **Verify the hash before replacing a cached
   file** — a truncated download must never overwrite a good puzzle.
5. Any failure at any step: keep the cache, log, carry on. Never a dialog.

Room schema:

```kotlin
@Entity data class PuzzleProgress(
    @PrimaryKey val pid: String,   // NOT the filename
    val state: State,              // UNSEEN, IN_PROGRESS, SOLVED
    val userMarksJson: String,     // the player's own marks only
    val assist: Boolean,
    val updatedAt: Long,
)
```

`pid` is a hash of the puzzle's content. The filename moves whenever the set is
regenerated — it has already moved three times during development — so keying
progress on `id` would silently mark the wrong puzzles complete after an
update.

## 4. `:app` — the UI

### The composite grid

A **single `Canvas`**, not nested lazy lists. 360 cells as individual
composables would be slow, and Compose's layout system cannot give sticky
headers on both axes without a fight. So: draw cells in a `DrawScope`,
hit-test taps against cell coordinates, and handle zoom/pan with
`Modifier.transformable` + `detectTapGestures`.

- **sticky headers** on both axes, drawn in the same canvas so they cannot
  drift out of sync with the cells.
- **default zoom fits width**, so you see the whole chart on opening.
- **blocked-out diagonal**: the triangle's unused half is drawn as inert, not
  as empty cells you might try to tap.
- **selection highlight** spanning the full row and column, which is how you
  read a logic grid.

### Screens

1. **Library** — the 50 puzzles, grouped by difficulty, showing state
   (unseen / in progress / solved) and whether a narrative exists.
2. **Solve** — composite grid + status bar + mark buttons; clue text in a
   bottom sheet; actions for check / undo / assist / reveal.
3. **Settings** — assist default, narrative-vs-canonical default, sync now,
   content version.

### Clue panel

Bottom sheet, draggable to three states (peek / half / full), because you need
clues and grid visible together. Narrative by default where one exists, with a
toggle to canonical — the canonical wording is what the puzzle was built from,
so it settles any ambiguity and must stay reachable.

### Feedback

Completing the answer sheet announces itself: **solved**, or *"not quite — N
marks are wrong"*. A check action at any time reports mistakes and names the
offending cells. Same contract as the TUI.

## 5. Phases, in dependency order

| phase | what | testable without a device? |
|---|---|---|
| **P0** | toolchain: JDK, Android cmdline-tools, SDK, Gradle wrapper, module skeleton that compiles | n/a |
| **P1** | `:core` — model, clue IR, `Board`, serialisation + conformance fixtures | **fully** |
| **P2** | `:data` — assets seed, manifest sync, Room, repositories | **mostly** (MockWebServer, Robolectric) |
| **P3** | `:app` — composite grid canvas, zoom/pan, selection, marking | ViewModel yes; rendering via Roborazzi |
| **P4** | clue bottom sheet, narrative/canonical toggle | yes |
| **P5** | library screen, progress persistence, resume | yes |
| **P6** | polish, accessibility, `adb` install/launch smoke | needs a device |

**P0 and P1 are the whole of the near-term value**, and both are achievable
with no device and no emulator. P2 is largely so. P3 onwards wants a real
screen.

## 6. Risks, honestly

- **No toolchain on this machine.** No JDK, SDK, ADB, Gradle or Kotlin was
  installed; the assumption that ADB was present did not hold. Installing a JDK
  and the Android command-line tools is phase P0, and it is a large download.
- **No emulator.** Hardware-accelerated emulation plus a system image is a much
  bigger ask than the SDK. Plan: JVM tests carry the load, Roborazzi covers
  rendering on the JVM, and device tests wait for a real phone over ADB.
- **Canvas grid is the riskiest UI work.** Hit-testing under a zoom/pan
  transform is fiddly and easy to get subtly wrong. Mitigation: keep the
  coordinate maths in a pure `GridGeometry` class in `:core`, unit-tested
  exhaustively, so the canvas only draws and forwards taps.
- **Compose/Kotlin version churn** — pin everything in a version catalog.
- **Only 5 of 50 puzzles are narrated.** By design for now; the app must treat
  a missing narrative as ordinary.

## 7. Review outcomes

The plan above was reviewed independently before any code was written. The
review is the reason several things look different from a straight port.

### Accepted — a blocker

**There was no canonical prose in the data.** The puzzle JSON carries only the
clue IR. The headline decision "narrative where one exists, canonical
otherwise" would therefore have required reimplementing ~375 lines of English
morphology in Kotlin -- irregular verb stems, do-support negation, article
insertion, `-ies/-ves/-es` pluralisation, number words, per-spine comparatives
-- for the path **45 of 50 puzzles take**. The easy case had been mistaken for
the common one.

Fixed in the content build instead: each puzzle now ships
`text.intro` + `text.clues`, pre-rendered. Ten lines of Python, one less Kotlin
subsystem, and every client is guaranteed to show identical wording.

### Accepted — a bug in the reference implementation

The closure's last-cell-standing rule did nothing when *zero* cells remained,
so ruling out every position for an item produced an unsatisfiable board that
reported no conflict and no mistake. Fixed in the Python (in the always-on
phase, since the state is equally impossible with assist off), fixtures
regenerated, and carried into the Kotlin as `ConflictReason.NowhereToGo`.

### Accepted — design changes

- **`Board` is immutable.** A mutable holder is the wrong thing for Compose to
  observe, and the Python `assist` setter assigns the flag before recomputing,
  so a conflict leaves it inconsistent. `setMark` returning a new state makes
  "a refused mark changes nothing" a type guarantee rather than a comment.
- **`ConflictReason` is structured**, not English. `:core` owns no UI copy.
- **`ignoreUnknownKeys`** on the JSON reader. Without it every puzzle fails to
  parse, since the files carry `spec`/`stats`/`solve`/`score` blocks.
- **`csp.py` is not ported at all** (~550 lines). `check` uses `mistakes()`,
  `reveal` uses the shipped solution, and validation happened at generation
  time.
- **Order-independence property test.** The fixtures replay one insertion
  order, so they could never catch a `HashMap`-ordering bug -- the likeliest
  Kotlin-specific failure.
- **Brute-force soundness oracle.** Fixtures prove Kotlin agrees with Python;
  they cannot prove either is right. For shapes small enough to enumerate, every
  derived mark is checked against all consistent completions. Soundness only --
  completeness is deliberately not asserted, because assist is weaker than full
  arc-consistency by design.
- **Fixtures are self-contained**, each carrying its own puzzle, so a
  regeneration cannot leave Kotlin replaying one puzzle against another's trace.
- **Phases resequenced**: the grid comes before sync. Sync is the lowest-risk,
  lowest-value work in the plan, because every puzzle is bundled in assets and a
  fresh install is fully playable offline before sync exists.
- **Drop the "cycle only at >= 44dp" rule.** It makes behaviour depend on zoom,
  and switches the fast path off at exactly the sizes where solving is slowest.
  "Tap selects; tap the selected cell to cycle" is unambiguous at any size.
- **Add nudge controls.** At 16dp cells a mis-tap is common and the only
  correction otherwise is zoom in, re-tap, zoom out. The terminal player has
  arrow keys for this reason. It also gives keyboard and switch access, and a
  coherent TalkBack story, nearly free.
- **The answer sheet belongs on the Solve screen.** It is the deliverable of
  the puzzle; "x/6 placed" is not a substitute.

### Not accepted — composite grid stays primary

The review argued per-pair grids should be the primary surface: ~37% of the
composite is dead triangle, it needs pan/zoom where per-pair never would, and a
`Canvas` is a single semantics node so all 360 cells are invisible to TalkBack.

Composite stays primary -- that is a product decision taken with the
measurements in hand. But the accessibility point is simply correct and cannot
be designed around, so **per-pair is built too**: as the accessible path, and
as the first grid built, because it de-risks everything downstream and yields a
playable app sooner. Additive, not a reversal. Accessibility moves out of "P6
polish" into the grid work itself.
